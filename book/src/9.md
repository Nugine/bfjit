# 9. LLVM JIT 方案设计

前面的章节使用 dynasm 直接生成 x86-64 机器码。本章开始做一个进阶扩展：保留 dynasm 后端，同时新增一个 LLVM JIT 后端，用同一套 Brainfuck IR 生成 LLVM IR，再交给 LLVM 生成本机代码。

## 内容规划

本扩展分为两章：

1. 本章调研技术方案，确定依赖、构建方式、命令行入口和运行方式。
2. 下一章实现 `src/bfjit_llvm.rs`，逐步说明 LLVM 后端如何生成函数、基本块、分支、回调和错误返回。

完成后，默认构建仍然运行 dynasm 后端；启用 `llvm` feature 后，可以通过 `--backend llvm` 切换到 LLVM 后端。

## 技术选型

Rust 调用 LLVM 大致有两条路：

- `llvm-sys`：直接暴露 LLVM C API，能力完整，但大量裸指针和 unsafe 代码会淹没教程重点。
- `inkwell`：在 `llvm-sys` 之上提供更安全、更符合 Rust 习惯的封装，适合解释 LLVM 的模块、函数、基本块和 builder 模型。

本教程选择 `inkwell`。它仍然要求系统中安装对应版本的 LLVM，但源代码更容易阅读，也更适合与 dynasm 版本做对照。

## MCJIT 与 ORC

LLVM 现在推荐 ORC JIT，MCJIT 已经进入维护状态。但是 `inkwell` 目前提供的高级 JIT 接口仍然是 MCJIT：

```rust,noplaypen
module.create_jit_execution_engine(OptimizationLevel::Default)
```

如果直接使用 ORC，需要通过 `llvm-sys` 调用 `LLVMOrcCreateLLJIT`、`LLVMOrcLLJITAddLLVMIRModule`、`LLVMOrcLLJITLookup` 等 C API。这样会显著增加 unsafe 代码和平台细节，不适合作为第一个 LLVM 版本。因此本教程采用 MCJIT，并在结构上保持后续迁移 ORC 的空间。

## 整体架构

LLVM 后端不重新解析 Brainfuck，而是复用第 3 章已有的 `BfIR`：

1. 读取 Brainfuck 源码。
2. 编译到 `Vec<BfIR>`。
3. 根据 `-o/--optimize` 决定是否调用已有优化器。
4. dynasm 后端把 IR 编译为汇编；LLVM 后端把 IR 编译为 LLVM IR。
5. 两个后端都使用同样大小的内存数组、同样的输入输出回调、同样的错误类型。

## Brainfuck IR 到 LLVM IR

每个 Brainfuck IR 可以自然地映射到 LLVM 指令：

| `BfIR` | LLVM 后端动作 |
| --- | --- |
| `AddPtr(n)` / `SubPtr(n)` | 把当前数据指针转换为整数，做加减和边界检查，再转回指针 |
| `AddVal(n)` / `SubVal(n)` | `load i8`，整数加减，`store i8` |
| `GetByte` / `PutByte` | 调用映射到 Rust 函数指针的外部函数 |
| `Jz` | 读取当前字节，条件跳转到循环体或循环出口 |
| `Jnz` | 读取当前字节，条件跳回循环体或进入循环出口 |

这里没有使用 SSA phi 节点保存数据指针，而是把指针放在一个 `alloca` 出来的局部槽位里。这样循环内部修改指针后，下一次循环条件仍然能读到最新指针，代码也更接近“寄存器变量”的直觉。

## 运行方式

默认运行仍然是 dynasm：

```bash
cargo run -- bf/hello.bf
```

运行 LLVM 后端需要启用 feature：

```bash
LLVM_SYS_181_PREFIX=/usr/lib/llvm-18 \
  cargo run --features llvm -- --backend llvm bf/hello.bf
```

优化选项仍然复用已有的 `-o/--optimize`：

```bash
LLVM_SYS_181_PREFIX=/usr/lib/llvm-18 \
  cargo run --release --features llvm -- --backend llvm bf/mendelbrot.bf -o
```
